# 编码 Agent 对比文章设计稿

## 目标

为 Nordlys 博客撰写一篇约 4000 字的中文文章，对比 Claude Code、OpenAI Codex CLI、earendil-works/pi 与 can1357/oh-my-pi（OMP）。文章面向已经使用过至少一种编码 Agent、正在判断是否更换工具的开发者。

文章发布日期写为 2026-06-15。所有产品能力和结论以该日期为信息截面；2026-06-15 后出现的功能、版本和产品变化不得倒灌进正文。

## 对比对象

- Claude Code：Anthropic 的编码 Agent 产品。
- Codex：OpenAI Codex CLI，而不是早期同名代码模型或仅在云端运行的 Codex 产品形态。
- Pi：`https://github.com/earendil-works/pi` 中的 Pi Agent Harness，不是 Inflection Pi，也不是 Raspberry Pi 项目。
- OMP：`https://github.com/can1357/oh-my-pi`，即 Oh My Pi。

由于 Pi 与 OMP 在 2026 年 6 月时的项目关系、功能和命名可能与当前文档不同，正文只能引用当时已经存在的仓库内容、发布记录或官方文档快照。若某项历史事实无法确认，文章不作确定性陈述。

## 核心判断

文章不比较单次模型跑分，也不评选统一的“最强 Agent”。模型会变化，相同 Harness 也可能接入不同模型。真正稳定并影响日常使用的差异是 Harness 如何组织模型、代码库、工具、权限和验证过程。

预期结论按场景给出：

- 希望少配置并直接进入成熟工作流的开发者，优先考虑 Claude Code。
- 已经使用 OpenAI 生态，同时重视沙箱、审批和脚本化的开发者，优先考虑 Codex CLI。
- 希望自由选择模型并亲自组装扩展能力的开发者，优先考虑 Pi。
- 希望保留开放模型选择，同时需要更完整的工程工具链的开发者，优先考虑 OMP。

这些是待资料验证的写作方向，不是预先写死的结论。若 2026-06-15 的官方资料不支持其中某项判断，应修改结论而不是挑选证据。

## 叙述方法

使用一个贯穿全文的任务：让四个 Agent 接手陌生仓库，找到一个跨文件问题，判断根因，修改实现及调用方，运行验证，并在任务扩大时拆分调查工作。

这条主线用于比较以下体验：

- 如何读取项目规则和建立代码库上下文；
- 如何搜索文件、符号和调用关系；
- 如何编辑代码并降低漏改风险；
- 如何运行命令，以及权限和沙箱怎样约束操作；
- 如何保存会话、压缩上下文或恢复工作；
- 如何扩展工具、接入外部系统和拆分子任务；
- 如何验证修改，而不是只生成补丁。

文章使用克制的第一人称表达判断，例如“我更愿意把这类任务交给……”。不得虚构使用时长、项目数量、成本、耗时或跑分。不能把阅读官方功能说明写成亲手使用体验。

## 文章结构

### 1. 为什么不再比较模型跑分

从同一个模型放进不同 Harness 后体验仍会不同切入，说明本文比较的是编码工作流，不是聊天能力。开头明确时间截面和产品范围。

### 2. 先把四个名字说清楚

简要介绍四个对比对象，说明 Codex 的具体产品形态，以及 Pi 和 OMP 不能仅按“原版与增强版”草率概括。只保留理解后文所需的背景。

### 3. 进入陌生仓库：谁先找到真正入口

沿着示例任务比较项目指令、文件读取、搜索方式和上下文管理。重点不是工具数量，而是 Agent 是否能少读无关内容，并复用仓库现有约定。

### 4. 修改跨文件代码：编辑之外还有代码智能

比较补丁机制、符号引用、调用方迁移、LSP 或等效能力。区分“模型能通过文本搜索猜到调用方”和“工具能基于语言服务器定位引用”。不把官方宣传中的成功率直接当作本文测试结果。

### 5. 运行命令：便利与控制权

比较审批、沙箱、可写目录、网络边界和默认权限。必须明确区分内置安全边界与依靠容器或外部环境实现的隔离，不能把“开放”或“可配置”写成“默认安全”。

### 6. 任务变大：上下文、自动化与子 Agent

比较长会话处理、非交互模式、CI 接入、子 Agent 和并行任务。功能不对等时直接说明，不为了表格完整而强行归类。

### 7. Pi 与 OMP：两种 Harness 取向

集中解释两者的差异：小核心与自行扩展，或更多内置工程工具与明确约束。评价上同时写收益和维护成本，避免把功能数量等同于质量。

### 8. 紧凑对比表

表格只保留会改变选型的维度：模型与供应商、默认工具、代码智能、扩展方式、权限与隔离、并行能力、自动化方式、上手成本。所有单元格使用短句；无法在历史资料中确认的项目写“未确认”或从表中删除。

### 9. 按场景选择

不设总冠军。分别回答省心使用、OpenAI 工作流、模型自由与深度工程工具四类需求。结论要能追溯到前文差异。

### 10. 选择的是 Harness，不只是模型

用具体判断收尾：经常切换模型的人更需要关注 Harness；只想稳定完成日常开发的人，应优先看默认流程、权限和验证是否合手。不要使用泛化的行业展望。

## 资料与证据规则

- 优先使用截至 2026-06-15 的官方文档、官方仓库 README、版本发布记录和源代码。
- 当前官网若已经更新，不能直接证明 2026 年 6 月已有相同能力；需要历史提交、版本标签或日期明确的发布记录佐证。
- 官方自述可证明产品提供某项能力，不能证明其效果优于其他产品。
- 不引用无法核实的排行榜、匿名评价或模糊的“开发者普遍认为”。
- 正文末尾列出主要资料链接，方便读者核对。

## 文风与 Humanizer-zh 检查

初稿完成后执行一次专门的人性化编辑：

- 删除“标志着”“重新定义”“革命性”等夸大表达；
- 删除没有来源的“行业认为”“用户普遍反馈”；
- 避免连续使用“此外”“然而”等连接词；
- 打散机械的三段式列举和等长句；
- 减少破折号、粗体和提纲式短句；
- 保留明确观点，但为事实、推断和个人偏好划清边界；
- 大声朗读时应像开发者复盘，而不是产品发布稿。

目标评分：直接性、节奏、信任度、真实性、精炼度总分不低于 45/50。

## 交付与验证

交付文件位于 `content/posts/`，使用现有文章 frontmatter：`title`、`description`、`publishedDate` 和 `tags`。`publishedDate` 固定为 `2026-06-15`。

完成后执行以下验证：

1. 检查 frontmatter 能被 Astro 内容集合解析；
2. 执行项目构建，确认文章页和 Pagefind 索引生成成功；
3. 启动生产预览并在浏览器打开文章页，检查标题、目录、表格、链接和代码样式；
4. 搜索正文中的未来版本、无来源跑分、夸张词和模糊归因；
5. 对最终文本执行 Humanizer-zh 质量评分。
