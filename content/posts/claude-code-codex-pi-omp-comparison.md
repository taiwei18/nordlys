过去一年，终端里的编码 Agent 多得有点难选。Claude Code 和 Codex 背靠模型厂商，Pi 与 OMP 则把更多选择权交给用户。它们都能读文件、改代码、跑命令，宣传页看起来也很接近。真正用来干活时，差别却不在输入框长什么样，而在模型外面那层 Harness。

Harness 决定 Agent 能看到什么，怎样修改文件，什么时候需要征求许可，以及犯错后能不能及时停下来。模型像发动机，Harness 更接近方向盘、刹车和仪表盘。只比较模型，很容易把这些差异漏掉。

本文讨论的是 2026 年 6 月中旬的产品状态。四个名字分别指 Anthropic Claude Code、OpenAI Codex CLI、[earendil-works/pi](https://github.com/earendil-works/pi) 和 [Oh My Pi](https://github.com/can1357/oh-my-pi)。更新速度这么快，半年后的功能表大概率已经变了。不过选工具时真正要问的问题，没那么容易过期。

## 我拿什么来比较

假设要把同一项工作交给四个 Agent：接手一个陌生仓库，找到搜索功能偶发显示旧结果的原因，修改实现，检查所有调用处，再运行构建和页面验证。

这不是一道刁钻的算法题。它更像平时真会遇到的活：问题横跨几个文件，仓库里已有约定，修完还得证明没有弄坏别处。Agent 至少要完成五件事：

1. 读项目说明，弄清目录和命令；
2. 搜到搜索入口及其调用关系；
3. 判断问题来自异步竞态，而不是随便加一个延迟；
4. 修改代码并运行针对性的验证；
5. 任务太大时，把调查拆开，又不能让几个执行者互相覆盖。

如果 Agent 只会吐出一段看似合理的补丁，这项工作就还没完成。

## Claude Code：成套工作流最省心

Claude Code 的长处是完整。它从一开始就不是给 Claude 模型套个终端聊天框，而是把代码读取、文件编辑、命令执行、项目说明和权限确认放进同一个工作循环。

进入陌生仓库时，它会读取 `CLAUDE.md` 一类项目指令。团队可以把构建命令、目录边界和代码规范写进去，不必每次重新解释。遇到前面的搜索竞态，它通常会先搜索入口和状态更新的位置，再读取相关文件，提出方案，然后改代码、跑命令。这个过程没有多少新概念，装好以后就能开始工作。

Claude Code 的定制入口也够多。MCP 用来接外部系统，Hooks 可以在工具调用前后执行确定性的脚本，Skills 保存重复流程，子 Agent 则能把相对独立的调查分出去。对多数团队来说，这些能力已经覆盖了“默认能用”和“以后还能加东西”之间的区域。

代价同样明确。它围绕 Anthropic 的产品和模型体验设计，虽然可以连接部分第三方平台，最佳路径仍然是 Claude。你得到的是一套整合较好的产品，而不是一盒随意替换零件的积木。权限机制能拦住不少危险操作，但允许一次命令不等于理解了它的全部后果，涉及部署、凭据和批量删除时仍要看清楚。

如果我只想让团队尽快用起来，不准备先花两天调 Harness，Claude Code 是最稳妥的起点。它未必在每个单项上最强，却很少要求用户先成为工具维护者。

## Codex CLI：边界清楚，也更适合脚本化

Codex CLI 的基本循环与 Claude Code 相似：读取本地仓库、修改文件、运行命令，再把结果留在工作区。它的特点是把模型、推理强度、权限和沙箱这些选择摆得比较明白。

对搜索竞态这种任务，Codex 可以在交互会话中调查和修改，也可以通过 `codex exec` 进入非交互流程。后者很适合可重复的工作，例如批量检查、CI 中的代码审阅，或者用固定提示词处理一组仓库。`AGENTS.md` 负责项目级说明，审批策略和沙箱则限制 Agent 能写哪里、何时可以执行命令。

我很看重这种边界感。Agent 需要自由才能完成任务，但“自由”不该等于继承整台机器的所有权限。尤其在不熟悉的仓库里，默认限制写入范围，再按需放开，比出事后检查命令历史靠谱。

Codex 的取舍也和 Claude Code相似：它首先服务 OpenAI 的模型与账户体系。喜欢 OpenAI 模型、已经在用 ChatGPT/Codex 订阅的人，认证和模型选择会很顺。若目标是频繁切换十几家供应商，或者自己重做整套工具协议，Codex 不是四者中最自由的那个。

它适合两类工作。一类是人在终端里盯着，要求 Agent 边做边解释；另一类是已经定义清楚、希望放进脚本重复执行的任务。前者靠交互控制，后者靠非交互模式和沙箱收紧边界。

## Pi：小核心不是功能少，而是让你自己决定

这里的 Pi 特指 `earendil-works/pi`。它把自己定义成一个精简的终端编码 Harness，核心之外的能力通过 TypeScript 扩展、Skills、提示模板、主题和 Pi packages 组合。它还提供统一的多供应商模型接口、Agent 运行时、TUI，以及用于嵌入其他程序的 SDK 和 RPC 模式。

这条路线很有吸引力。你可以给普通任务用便宜模型，复杂重构换更强的模型，也能接本地服务。某个团队需要内部搜索工具，可以写扩展；另一支团队只想保留四个基础工具，也不用背着一大套功能运行。

但 Pi 的“少”不会自动替你做决定。回到那次搜索竞态，如果想要符号级引用、浏览器验证或特定的审批流程，需要确认当前安装包含什么，再选择扩展或外部工具。配置得好，它会非常贴合个人工作方式；配置得一般，它就只是一个能调用 Shell 的模型循环。

安全边界更需要单独说明。Pi 官方文档明确写着，它默认以启动进程的用户权限运行，没有内置的文件系统、进程、网络或凭据权限隔离。需要更强边界时，应放进容器或沙箱。这个设计没有遮掩，但使用者必须真的处理它，不能把“开源、可控”自动理解成“默认安全”。

我会把 Pi 推荐给喜欢自己搭工具的人。他们通常已经知道需要哪些模型、哪些命令不能开放，也愿意维护几段扩展代码。若只是想安装后立刻得到一套团队级工作流，Pi 反而可能让人多做一轮选择题。

## OMP：把 IDE 和工程工具塞进 Harness

OMP 的全名是 Oh My Pi。它与 Pi 生态同源，但本文对比的 `earendil-works/pi` 和 OMP 不是简单的“原版与插件包”关系。OMP 的仓库说明显示，它从 `badlogic/pi-mono` 分化而来，选择了另一条路：不再尽量保持小核心，而是把常用工程能力直接做进产品。

在 2026 年 6 月 15 日的仓库快照中，OMP 已经提供多供应商模型、内置 LSP 与 DAP、持久 Python/JavaScript 执行环境、子 Agent、哈希锚定编辑、浏览器和网页读取等工具。它的口号“把 IDE 接进编码 Agent”很准确。

这些东西放到跨文件修改里就不抽象了。文本搜索能找到变量名，LSP 引用能识别重导出、别名和符号关系；普通补丁依赖旧文本完全匹配，哈希锚定编辑会在文件已经变化时拒绝落盘；日志不够看时，DAP 可以直接检查线程、堆栈和变量。对大型 TypeScript、Rust 或 Go 项目，这些能力会改变 Agent 的做事方式。

OMP 的子 Agent 也不只是多开几个聊天窗口。任务可以进入隔离工作区，执行者返回结构化结果，主 Agent 再合并判断。拆分“找竞态入口”和“检查测试覆盖”很合适；让两个执行者同时改同一文件，依然是坏主意。并行不是越宽越快，边界划错以后只会更忙。

功能密度高带来新的成本。工具多，规则也多；精细的读取和编辑协议能减少误改，但模型得先学会正确使用。与 Claude Code 相比，OMP 更像一张铺满设备的工作台。熟悉以后效率很高，第一次坐下时则不一定轻松。

我不会因为工具数量就判定 OMP 更强。它真正适合的是已经知道自己为何需要 LSP、调试器、持久执行环境和多模型路由的人。只改几个配置文件时，这套装备可能过重；接手跨语言仓库时，它的价值才会出来。

## 放在一张表里看

| 维度           | Claude Code                  | Codex CLI                     | Pi                                      | OMP                                     |
| -------------- | ---------------------------- | ----------------------------- | --------------------------------------- | --------------------------------------- |
| 主要取向       | 完整、成熟的 Claude 工作流   | OpenAI 生态与清楚的执行边界   | 精简核心，自行扩展                      | 内置较完整的工程工具                    |
| 模型选择       | 以 Claude 为中心             | 以 OpenAI 模型为中心          | 多供应商，可接自定义模型                | 多供应商，并支持按角色路由              |
| 项目说明       | `CLAUDE.md`                  | `AGENTS.md`                   | 上下文文件与 Skills                     | 兼容多种规则格式，并有 Skills           |
| 代码检索与编辑 | 内置读取、搜索和编辑工具     | 本地读取、修改与命令执行      | 基础工具由核心和扩展组合                | 内置搜索、哈希锚定编辑、AST 与 LSP 工具 |
| 隔离方式       | 权限确认与可配置规则         | 审批策略和沙箱较突出          | 默认继承当前进程权限，建议外部沙箱      | 有权限工具与隔离执行选项，仍需正确配置  |
| 扩展           | MCP、Hooks、Skills、子 Agent | MCP、Skills、脚本和非交互模式 | TypeScript 扩展、Skills、模板、packages | Skills、工具、持久执行环境、子 Agent    |
| 上手成本       | 低                           | 低到中                        | 中，取决于定制程度                      | 中到高                                  |
| 更适合         | 想尽快进入稳定工作流         | OpenAI 用户与自动化任务       | 喜欢自己组装 Harness 的开发者           | 复杂仓库和深度工程任务                  |

这张表故意没有“代码质量”一行。最终结果受模型、提示、仓库质量和验证方式共同影响，写一个星级评分只会制造确定感。同一个 Agent 在结构清楚的项目里表现很好，换到没有测试、命名混乱的旧系统里，也会踩坑。

## 我会怎样选

如果是个人项目，又想尽快开始，我会先选 Claude Code 或 Codex。两者的默认路径都比较完整。偏爱 Claude、经常做探索式修改，选 Claude Code；主要使用 OpenAI 模型，或者想把任务放进脚本和 CI，选 Codex。

如果我明确知道自己需要多模型，而且愿意维护扩展，Pi 更合适。它不会替我预装所有答案，换来的是更少的框架意见。这个自由很实在，也确实要自己付维护成本。

如果工作对象是大型仓库，跨语言、重构和调试很多，我会认真考虑 OMP。LSP、DAP 和精细编辑协议不是装饰，它们正好覆盖编码 Agent 最容易靠猜的地方。前提是团队愿意理解这些工具，并给权限划出边界。

团队选型还要再加一条：不要只看最熟练的那个人。负责人花一周调好的 Pi 或 OMP，交给其他人未必顺手；Claude Code 的默认体验容易推广，却可能不符合团队的模型与数据策略；Codex 的沙箱清楚，也不代表所有自动化命令都可以无人值守。

最靠谱的办法不是连续问四个 Agent 同一道算法题，而是拿仓库里一项真实、可回滚的任务试跑。观察它读了多少无关文件，是否先理解规则，修改后跑了什么验证，遇到权限问题怎么处理。最后再看账单。

## 选择的是工作方式

编码 Agent 的产品页总在谈模型能力，但日常体验往往被更琐碎的东西决定：搜索是否准确，补丁会不会落错位置，命令有没有边界，长对话压缩后还记不记得目标。

Claude Code 和 Codex 给出的是两套厂商整合方案。Pi 把 Harness 留成可组装的底座。OMP 则把许多 IDE 与工程能力搬进底座。它们没有排成一条从弱到强的直线，只是把复杂度放在了不同地方。

不想维护工具，就为好的默认值付费。想掌控模型和流程，就接受配置与维护。真正糟糕的选择，是拿到完整机器却只会让它生成代码，或者装了精简底座，又期待它替你处理所有工程细节。
